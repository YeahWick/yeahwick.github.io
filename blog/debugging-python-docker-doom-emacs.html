Debugging Python in Docker Containers with Doom Emacs

January 15, 2026

The Container Debugging Challenge

In my previous post, I covered how to debug Python using DAP in Doom Emacs. But modern development often means your code runs inside Docker containers, not directly on your machine. How do you set breakpoints and step through code when Python is running in an isolated container? The answer is remote debugging with debugpy.

This guide walks you through setting up a complete Docker debugging workflow that lets you use all the DAP features we covered before—breakpoints, variable inspection, stepping, and the REPL—while your code executes inside a container.

The Architecture

Remote debugging works by having the Python process in the container connect back to your debugger (or vice versa). Here's what happens:

  1. Your containerized Python app starts with debugpy listening on a port
  2. That port is exposed from the container to your host machine
  3. Doom Emacs connects to that port using DAP's "attach" mode
  4. You debug as if the code were running locally

Let's set this up step by step.

Project Structure

We'll create a simple Flask application to demonstrate the debugging workflow. Here's our project structure:

my-docker-app/
├── app/
│   ├── __init__.py
│   ├── main.py
│   └── utils.py
├── Dockerfile
├── docker-compose.yml
├── docker-compose.debug.yml
└── requirements.txt

The Example Application

First, let's create our Flask application. This simple API calculates statistics for numbers:

# app/main.py
from flask import Flask, request, jsonify
from app.utils import calculate_stats

app = Flask(__name__)


@app.route('/health')
def health():
    return jsonify({"status": "healthy"})


@app.route('/stats', methods=['POST'])
def stats():
    data = request.get_json()
    numbers = data.get('numbers', [])

    if not numbers:
        return jsonify({"error": "No numbers provided"}), 400

    result = calculate_stats(numbers)
    return jsonify(result)


if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
# app/utils.py
def calculate_mean(numbers):
    """Calculate the arithmetic mean."""
    total = sum(numbers)
    return total / len(numbers)


def calculate_variance(numbers):
    """Calculate variance from the mean."""
    mean = calculate_mean(numbers)
    squared_diffs = [(x - mean) ** 2 for x in numbers]
    return calculate_mean(squared_diffs)


def calculate_stats(numbers):
    """Calculate comprehensive statistics."""
    mean = calculate_mean(numbers)
    variance = calculate_variance(numbers)
    std_dev = variance ** 0.5

    return {
        "count": len(numbers),
        "mean": round(mean, 4),
        "variance": round(variance, 4),
        "std_dev": round(std_dev, 4),
        "min": min(numbers),
        "max": max(numbers)
    }
# app/__init__.py
# Package marker
# requirements.txt
flask==3.0.0
debugpy==1.8.0

Docker Configuration

Now let's create the Docker configuration. We'll have two compose files: one for production and one for debugging.

# Dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app/ ./app/

# Default command for production
CMD ["python", "-m", "app.main"]
# docker-compose.yml (production)
services:
  api:
    build: .
    ports:
      - "5000:5000"
    environment:
      - FLASK_ENV=production

For debugging, we need a separate compose file that enables debugpy:

# docker-compose.debug.yml
services:
  api:
    build: .
    ports:
      - "5000:5000"
      - "5678:5678"  # debugpy port
    environment:
      - FLASK_ENV=development
      - DEBUGPY_ENABLE=1
    volumes:
      - ./app:/app/app:ro  # Mount source for live editing
    command: >
      python -m debugpy
      --listen 0.0.0.0:5678
      --wait-for-client
      -m app.main

Understanding the Debug Configuration

Let's break down the key parts of docker-compose.debug.yml:

  • ports: "5678:5678" - Exposes the debugpy port so Emacs can connect
  • volumes: ./app:/app/app:ro - Mounts your local source code into the container. This is crucial for Emacs to match breakpoints to files
  • --listen 0.0.0.0:5678 - Makes debugpy listen on all interfaces (required for Docker networking)
  • --wait-for-client - Pauses execution until the debugger connects. Remove this if you want the app to start immediately

Configuring DAP in Doom Emacs

Add a debug template for Docker remote debugging in your ~/.doom.d/config.el:

;; ~/.doom.d/config.el

(after! dap-mode
  ;; Docker remote debugging template
  (dap-register-debug-template
   "Python :: Docker Attach"
   (list :type "python"
         :request "attach"
         :name "Docker Debug"
         :connect (list :host "localhost" :port 5678)
         :pathMappings (vector
                        (list :localRoot "${workspaceFolder}/app"
                              :remoteRoot "/app/app"))
         :justMyCode nil))

  ;; Alternative: attach without waiting
  (dap-register-debug-template
   "Python :: Docker Attach (Running)"
   (list :type "python"
         :request "attach"
         :name "Docker Debug (Running)"
         :connect (list :host "localhost" :port 5678)
         :pathMappings (vector
                        (list :localRoot "${workspaceFolder}/app"
                              :remoteRoot "/app/app"))
         :justMyCode nil)))

Path Mappings Explained

The :pathMappings setting is critical. It tells DAP how to translate between:

  • localRoot - Where the source files are on your machine
  • remoteRoot - Where the same files exist inside the container

Without correct path mappings, breakpoints won't work because DAP can't match your local file /home/you/project/app/main.py to the container's /app/app/main.py.

The Debugging Workflow

Now let's put it all together. Here's the complete workflow for debugging your containerized Python application:

Step 1: Start the Container in Debug Mode

# Terminal
docker-compose -f docker-compose.debug.yml up --build

You'll see output like:

api-1  | Listening for debugpy on 0.0.0.0:5678...

The container is now waiting for your debugger to connect.

Step 2: Open Your Project in Emacs

Open the project directory in Emacs. Make sure you're at the project root so that path mappings work correctly.

Step 3: Set Breakpoints

Open app/utils.py and set a breakpoint in calculate_stats:

SPC d b b    ; On the line: mean = calculate_mean(numbers)

The red dot appears in your local file, but it will trigger when the code runs in Docker.

Step 4: Attach the Debugger

SPC d d      ; Start debugging
; Select "Python :: Docker Attach" from the list

You'll see DAP connect, and the container will continue execution:

api-1  | * Running on http://0.0.0.0:5000

Step 5: Trigger Your Code

In another terminal, make a request to your API:

curl -X POST http://localhost:5000/stats \
  -H "Content-Type: application/json" \
  -d '{"numbers": [10, 20, 30, 40, 50]}'

Execution pauses at your breakpoint! You're now debugging code running inside Docker.

Step 6: Debug as Normal

All the DAP features work exactly as they do locally:

SPC d n      ; Step over
SPC d i      ; Step into calculate_mean
SPC d e e    ; Evaluate expression at point
SPC d e r    ; Open REPL to inspect variables

The Locals window shows variables from inside the container, and you can evaluate any Python expression in the container's context.

Alternative: Programmatic Debug Activation

Sometimes you want the app to run normally and only start debugging under certain conditions. Instead of using --wait-for-client, you can activate debugging programmatically:

# app/main.py
import os
from flask import Flask, request, jsonify
from app.utils import calculate_stats

app = Flask(__name__)

# Enable debugging if environment variable is set
if os.environ.get('DEBUGPY_ENABLE'):
    import debugpy
    debugpy.listen(("0.0.0.0", 5678))
    print("Debugpy listening on port 5678")

    # Optionally wait for client
    if os.environ.get('DEBUGPY_WAIT'):
        print("Waiting for debugger to attach...")
        debugpy.wait_for_client()


@app.route('/health')
def health():
    return jsonify({"status": "healthy"})


@app.route('/stats', methods=['POST'])
def stats():
    data = request.get_json()
    numbers = data.get('numbers', [])

    if not numbers:
        return jsonify({"error": "No numbers provided"}), 400

    # You can also trigger a breakpoint programmatically
    # debugpy.breakpoint()

    result = calculate_stats(numbers)
    return jsonify(result)


if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000, debug=False)

Update your debug compose file:

# docker-compose.debug.yml (programmatic version)
services:
  api:
    build: .
    ports:
      - "5000:5000"
      - "5678:5678"
    environment:
      - FLASK_ENV=development
      - DEBUGPY_ENABLE=1
      # - DEBUGPY_WAIT=1  # Uncomment to wait for debugger
    volumes:
      - ./app:/app/app:ro

This approach lets you:

  • Start the app without waiting for a debugger
  • Attach the debugger whenever you need it
  • Use debugpy.breakpoint() to set breakpoints in code
  • Control debugging behavior with environment variables

Debugging Django Applications

For Django, the setup is similar. Here's a Django-specific configuration:

# manage.py (add at the top)
import os
import sys

if os.environ.get('DEBUGPY_ENABLE'):
    import debugpy
    debugpy.listen(("0.0.0.0", 5678))
    if os.environ.get('DEBUGPY_WAIT'):
        debugpy.wait_for_client()


def main():
    os.environ.setdefault('DJANGO_SETTINGS_MODULE', 'myproject.settings')
    # ... rest of manage.py
# docker-compose.debug.yml for Django
services:
  web:
    build: .
    ports:
      - "8000:8000"
      - "5678:5678"
    environment:
      - DEBUGPY_ENABLE=1
    volumes:
      - ./myproject:/app/myproject:ro
    command: python manage.py runserver 0.0.0.0:8000

Debugging Background Workers (Celery)

Debugging Celery workers requires attaching to a different process. Use a separate debug port:

# docker-compose.debug.yml with Celery
services:
  api:
    # ... api config with port 5678

  worker:
    build: .
    ports:
      - "5679:5679"  # Different port for worker
    environment:
      - DEBUGPY_ENABLE=1
      - DEBUGPY_PORT=5679
    volumes:
      - ./app:/app/app:ro
    command: >
      python -m debugpy
      --listen 0.0.0.0:5679
      -m celery
      -A app.celery worker --loglevel=info

Add a corresponding DAP template:

(dap-register-debug-template
 "Python :: Docker Worker"
 (list :type "python"
       :request "attach"
       :name "Docker Worker Debug"
       :connect (list :host "localhost" :port 5679)
       :pathMappings (vector
                      (list :localRoot "${workspaceFolder}/app"
                            :remoteRoot "/app/app"))
       :justMyCode nil))

Debugging Tests in Docker

Running and debugging tests inside Docker follows the same pattern:

# docker-compose.test.yml
services:
  test:
    build: .
    ports:
      - "5678:5678"
    environment:
      - DEBUGPY_ENABLE=1
    volumes:
      - ./app:/app/app:ro
      - ./tests:/app/tests:ro
    command: >
      python -m debugpy
      --listen 0.0.0.0:5678
      --wait-for-client
      -m pytest tests/ -v -s

Run tests with debugging:

docker-compose -f docker-compose.test.yml up

Then attach with SPC d d and select your Docker attach template.

Troubleshooting

Breakpoints Not Hitting

The most common issue is incorrect path mappings. Verify them:

  1. Check where your code lives locally: /home/user/project/app/main.py
  2. Check where it's mounted in the container: /app/app/main.py
  3. Ensure :localRoot and :remoteRoot match these paths

You can also verify by adding a log point instead of a breakpoint—if the log appears in the output, your path mappings are correct.

Connection Refused

If DAP can't connect:

  • Ensure the container is running: docker ps
  • Check the port is exposed: docker port container_name
  • Verify debugpy is listening: docker logs container_name
  • Try connecting with netcat: nc -zv localhost 5678

Debugger Disconnects

If the debugger disconnects unexpectedly:

  • Check for container restarts: docker-compose logs -f
  • Ensure your code doesn't call sys.exit()
  • For long-running tasks, the connection might timeout—reconnect as needed

Source Not Matching

If line numbers seem off:

  • Ensure volumes are mounted with the latest code
  • Rebuild the container after code changes: docker-compose build
  • For development, use volume mounts instead of copying files in the Dockerfile

Best Practices

  • Use separate compose files: Keep debug configuration separate from production
  • Don't commit debug code: Use environment variables to conditionally enable debugpy
  • Mount source as read-only: Use :ro to prevent accidental container writes
  • Use .dockerignore: Exclude __pycache__, .pyc, and IDE files
  • Document the workflow: Add debugging instructions to your project README
  • Use consistent ports: Stick to 5678 for debugpy to maintain team consistency

Quick Reference: Docker Debugging Commands

# Start container in debug mode
docker-compose -f docker-compose.debug.yml up --build

# Start without waiting for debugger
docker-compose -f docker-compose.debug.yml up -d

# View container logs
docker-compose -f docker-compose.debug.yml logs -f

# Rebuild after Dockerfile changes
docker-compose -f docker-compose.debug.yml up --build

# Stop containers
docker-compose -f docker-compose.debug.yml down

Emacs DAP Quick Reference for Docker

SPC d d        ; Start debugging, select Docker template
SPC d b b      ; Set breakpoint (works for container code!)
SPC d n        ; Step over
SPC d i        ; Step into
SPC d o        ; Step out
SPC d c        ; Continue
SPC d q        ; Disconnect from container
SPC d e r      ; REPL (evaluates in container context)

Conclusion

Debugging containerized Python applications doesn't have to mean abandoning your carefully crafted Emacs workflow. With debugpy and DAP's remote debugging capabilities, you get the full debugging experience—breakpoints, stepping, variable inspection, and the REPL—while your code runs in a proper container environment.

The key is getting your path mappings right and using a separate compose file for debug mode. Once set up, the workflow becomes second nature: start the container, attach the debugger, and debug as if everything were running locally.

This approach works for Flask, Django, Celery workers, and even test suites. No more print statements scattered through containerized code—just set a breakpoint and step through.
